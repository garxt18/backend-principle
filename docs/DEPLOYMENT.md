# Deployment Guide

Put Backend Playground on the internet so your friends can sign up. All options use the same `Dockerfile`,
so what you tested locally is exactly what runs online.

## "Do I have to wake the server up?" - pick the right option

| Option | Cost | Sleeps? | Effort | Notes |
|---|---|---|---|---|
| **A. Render free + Neon Postgres + a free pinger** | free | **No** (the pinger keeps it awake) | ~15 min, browser only | 512 MB RAM; one app 24/7 fits in Render's 750 free hours/month |
| **B. Oracle Cloud "Always Free" VM** | free forever | **Never** | ~45 min | A real server (up to 4 ARM cores / 24 GB RAM); needs a card for identity check |
| **C. Small paid VPS** (Hetzner, DigitalOcean, Lightsail...) | ~$4-6/month | Never | ~30 min | Same steps as B, simplest always-on setup |
| **D. Render paid instance** | from ~$7/month | Never | 1 click | Keep option A, just change the instance type |

Why not the others on a free plan: Koyeb's free instance also scales to zero (after 1 hour idle) and has
0.1 vCPU, which makes Spring Boot slow to start; Railway and Fly.io bill usage. Plans change - check each
provider's pricing page.

Two free-tier facts that matter (as of 2026):
- A free Render web service **sleeps after 15 minutes without traffic** and takes about **a minute** to wake up.
- A free **Render Postgres is deleted 30 days after it is created**. That is why the Blueprint below uses
  **Neon** (free Postgres that does not expire) instead - your friends' progress is never lost.

Before any option: push your latest code to GitHub (`git push`).

## Option A - Render (free) + Neon (free Postgres) + a pinger

### 1. Create the database on Neon (3 minutes)

1. Sign up at https://neon.tech (GitHub login, no card).
2. Create a project (region close to your Render region, e.g. both in Singapore or both in Frankfurt).
3. On the dashboard click **Connect** and copy the connection string. It looks like
   `postgresql://neondb_owner:xxxx@ep-something.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
   (The app converts this to Spring's JDBC settings by itself - `DatabaseUrlEnvironmentPostProcessor`.)

Neon's free plan pauses the *database* after 5 minutes idle and wakes it in well under a second on the next
query, so you do not need to keep it awake - only the web service.

### 2. Deploy the app on Render (10 minutes)

1. Create an account at https://render.com (sign in with GitHub).
2. Dashboard -> **New** -> **Blueprint** -> select the `backend-principle` repository.
3. Render reads `render.yaml` and asks for the values marked `sync: false`:
   - `DATABASE_URL` - the Neon connection string from step 1
   - `APP_ADMIN_EMAIL` - your email (becomes the admin account)
   - `APP_ADMIN_PASSWORD` - at least 12 characters
4. Click **Apply**. Render builds the Docker image (~5-8 minutes the first time) and starts it.
5. Open the URL Render shows (e.g. `https://backend-playground.onrender.com`) and log in.

`APP_JWT_SECRET` is generated by Render, and `APP_SECURE_COOKIE=true` because Render serves HTTPS.
Every `git push` to your main branch redeploys automatically.

Already deployed with the old Blueprint (Render Postgres)? Create the Neon database, then in Render open the
web service -> **Environment** -> set `DATABASE_URL` to the Neon string -> save (it redeploys; Flyway creates
the tables on Neon). To keep existing data, first copy it:
`pg_dump "<render external url>" | psql "<neon url>"`. Then delete the Render database.

### 3. Stop it from sleeping (2 minutes)

Something has to visit the app at least every 15 minutes. Use a free external pinger:

- **cron-job.org** (recommended): sign up -> **Create cronjob** -> URL
  `https://<your-app>.onrender.com/actuator/health/liveness` -> every **10 minutes** -> save.
- or **UptimeRobot**: New monitor -> HTTP(s) -> same URL -> interval 5 minutes. (You also get an email when
  the site is down.)
- Backup: this repo has `.github/workflows/keep-awake.yml`. Set a repository variable `KEEP_AWAKE_URL`
  (GitHub -> Settings -> Secrets and variables -> Actions -> **Variables**) to your app URL and it pings every
  10 minutes. GitHub can delay scheduled runs, so keep cron-job.org as the main pinger.

The liveness endpoint does not touch the database, so the pinger keeps the app awake while Neon can still
pause. One service awake 24/7 uses about 720-744 of Render's 750 free hours per month - do not run a second
always-awake free service in the same Render account.

Memory: the free instance has 512 MB. `render.yaml` sets a small-footprint JVM (`JAVA_OPTS`). If you still see
out-of-memory restarts in the logs, move to a paid instance (option D).

## Option B - Oracle Cloud "Always Free" VM (never sleeps, free)

Oracle's Always Free tier includes Ampere (ARM) VMs with up to 4 cores and 24 GB RAM in total - far more than
this app needs - and they do not expire. You run the same `docker-compose.prod.yml` as option C.

1. Sign up at https://www.oracle.com/cloud/free/ (a card is used only to verify you; Always Free resources
   are not charged). Pick a **home region** near you - you cannot change it later.
2. **Create a VM**: Compute -> Instances -> Create. Image **Ubuntu 22.04/24.04**, shape **VM.Standard.A1.Flex**
   (Ampere) with **1-2 OCPU and 6-12 GB RAM**. Add your SSH public key. If it says *out of capacity*, try another
   availability domain or try again later - this is common in busy regions.
3. **Open ports 80 and 443**: in the instance's VCN -> Security List -> add ingress rules for TCP 80 and 443 from
   `0.0.0.0/0`. Oracle's Ubuntu images also have their own firewall, so on the VM run:
   ```bash
   sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
   sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
   sudo netfilter-persistent save
   ```
4. **Free domain**: create a subdomain at https://www.duckdns.org (e.g. `mybackend.duckdns.org`) pointing at the
   VM's public IP. Caddy needs a domain to get a free HTTPS certificate.
5. Follow **Option C, steps 3-6** below (install Docker, clone, `.env` with `DOMAIN=mybackend.duckdns.org`,
   `docker compose -f docker-compose.prod.yml up -d --build`). Every image used here supports ARM.

## Option C - your own server with Docker Compose + HTTPS

You rent a small Linux VM, install Docker, and run `docker-compose.prod.yml`. **Caddy** sits in front and gets
free HTTPS certificates from Let's Encrypt automatically. Postgres and the app are not exposed to the internet;
only Caddy (ports 80/443) is.

```
Internet --HTTPS--> Caddy (:443) --> app (:8080) --> db (:5432, private)
```

1. **Create a server**: Ubuntu 24.04, 1 GB RAM minimum (2 GB is comfortable). Any provider works
   (DigitalOcean, Hetzner, AWS Lightsail, or Oracle Cloud's free VM from option B).
2. **Point a domain** at it: create an `A` record like `learn.yourdomain.com -> <server IP>`.
   (No domain? Free subdomains exist, e.g. DuckDNS.)
3. **Install Docker** on the server:
   ```bash
   ssh root@<server-ip>
   curl -fsSL https://get.docker.com | sh
   ```
4. **Get the code and configure it**:
   ```bash
   git clone https://github.com/garxt18/backend-principle.git
   cd backend-principle
   cp .env.example .env
   nano .env      # set DOMAIN, DB_PASSWORD, APP_JWT_SECRET (openssl rand -base64 48), admin email/password
   ```
5. **Start it**:
   ```bash
   docker compose -f docker-compose.prod.yml up -d --build
   docker compose -f docker-compose.prod.yml logs -f app     # wait for "Started PlaygroundApplication"
   ```
6. Open `https://learn.yourdomain.com`. Caddy fetches the certificate on the first request.

Updating after you push new code:

```bash
cd backend-principle && git pull
docker compose -f docker-compose.prod.yml up -d --build
```

Backups (run daily with cron):

```bash
docker compose -f docker-compose.prod.yml exec -T db pg_dump -U playground playground | gzip > backup-$(date +%F).sql.gz
```

Firewall: allow only SSH (22), HTTP (80) and HTTPS (443) - e.g. `ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw enable`.

## Option E - other container platforms

Any platform that runs a Dockerfile works. Give it:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the `postgres://...` connection string of a PostgreSQL database (or `DB_URL` + `DB_USERNAME` + `DB_PASSWORD`) |
| `APP_JWT_SECRET` | 32+ random characters |
| `APP_SECURE_COOKIE` | `true` (the platform serves HTTPS) |
| `PORT` | usually set by the platform automatically; the app listens on it |
| `APP_ADMIN_EMAIL`, `APP_ADMIN_PASSWORD` | optional first admin |

Health check path: `/actuator/health/readiness`.

## Production checklist

- [ ] `APP_JWT_SECRET` is long and random, and never committed to Git
- [ ] `APP_SECURE_COOKIE=true` (the site is served over HTTPS)
- [ ] The database is not reachable from the internet
- [ ] The database will not expire (Neon or your own server - not a free Render Postgres)
- [ ] Something pings the app every 10 minutes if it runs on a free plan that sleeps (option A, step 3)
- [ ] Database backups are scheduled (options B/C) or provided by the platform
- [ ] An admin account exists (`APP_ADMIN_EMAIL` / `APP_ADMIN_PASSWORD`), then those two variables can be removed
- [ ] `LOG_FORMAT=ecs` for JSON logs
- [ ] You opened the site on your phone and it works
